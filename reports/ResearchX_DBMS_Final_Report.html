ABSTRACT

ResearchX is a database-centered platform designed to help students discover research literature, maintain university project records and explore semantic similarity between research topics. A conventional keyword search can miss relevant content when descriptions use different words for related concepts. ResearchX integrates a normalized PostgreSQL database with vector-based text comparison to address this gap.

The relational schema comprises 11 tables representing user roles, application users, research domains, student projects, project-domain associations, academic papers, authors, paper-author associations, faculty reviews, audit records and embedding references. The implementation uses primary/foreign keys, composite keys, unique and check constraints, indexes, stored functions, a faculty-review procedure, transaction handling and database triggers to demonstrate core DBMS concepts.

A 384-dimensional MiniLM encoder transforms research text into numerical vectors stored in PostgreSQL through pgvector. Cosine-distance queries rank locally indexed projects and saved papers according to conceptual alignment. OpenAlex integration provides live literature search; selected papers and their authors can be persisted in the relational database. A responsive Next.js/TypeScript interface supports browsing, project submission, review workflows and similarity search.

The project includes implementation scripts, SQL execution evidence, and automated verification of API, database and browser workflows. The platform is an academic demonstration, and its similarity scores are not plagiarism or originality judgments. The overall outcome is a practical integration of relational database design, advanced SQL programming and semantic retrieval in a single research-oriented application.

Keywords: DBMS, PostgreSQL, ER model, relational mapping, pgvector, MiniLM, cosine similarity, OpenAlex, Next.js.

1. INTRODUCTION

1.1 Overview

ResearchX — Intelligent Research Discovery & Project Similarity Platform is a web-based academic research management application developed as a DBMS mini-project. It combines conventional relational data management with semantic retrieval so that students can register projects, browse related proposals, discover scholarly literature, save useful papers, and inspect conceptual similarity within a locally indexed collection.

Research topics are often described using different words even when they address related problems. A conventional title or keyword search may overlook this connection. ResearchX addresses this limitation using a 384-dimensional sentence embedding model together with PostgreSQL's pgvector extension while retaining relational integrity for users, projects, research domains, paper authorships, review decisions and audit histories.

The project uses PostgreSQL 16 as its primary DBMS, the pgvector extension for vector storage and cosine-distance retrieval, Next.js 14 and TypeScript for the application, Tailwind CSS for interface styling, OpenAlex for live academic literature discovery, and Xenova/all-MiniLM-L6-v2 for local embeddings.

1.2 Objectives

  • Design and implement a normalized relational schema with primary keys, foreign keys, UNIQUE and CHECK constraints.
  • Map the conceptual ER model systematically to 11 implemented PostgreSQL relations.
  • Demonstrate DDL, DML, aggregation, nested and correlated queries, joins, procedures, functions and triggers.
  • Support project registration, status updates, faculty review and persistent audit records using transactional SQL.
  • Retrieve related local projects and saved papers using 384-dimensional embeddings and cosine similarity.
  • Retrieve live literature through OpenAlex and persist selected records with author associations.
  • Provide a usable browser interface for the principal database workflows.

1.3 Scope and Boundaries

The platform's semantic search compares only the projects and research papers already indexed in its local database; OpenAlex search is a separate live discovery workflow. A cosine similarity score denotes vector-level conceptual alignment and does not establish plagiarism, originality or the statistical probability of duplication.

ResearchX uses seeded demonstration student and faculty profiles. Although the database stored procedure checks a reviewer's role, the public-facing demonstration does not implement a production authentication or authorization system. Therefore the application is intended for coursework demonstration and controlled use, not unsecured production deployment.

1.4 System Architecture

2. PROBLEM DEFINITION

2.1 Problem Statement

Students developing academic projects need a reliable way to understand what has already been attempted, find supporting literature and recognize closely related proposals. These records are typically scattered across different lists or external websites, and a plain keyword comparison often fails to identify semantically similar descriptions.

A university project catalogue must also preserve accurate relationships among users, roles, projects, domains, research papers, authors and faculty reviews. Updates should remain consistent when multiple database records are created, modified or deleted.

2.2 Limitations of Existing Approaches

  • Keyword-only matching does not consistently capture synonymy and paraphrased research ideas.
  • Manual tracking of projects and reviews can duplicate records and lose approval history.
  • Research papers and authors have many-to-many associations that are error-prone in denormalized storage.
  • Independent similarity indexes can drift out of sync with relational records after partial failures.
  • Unstructured forms and fragmented interfaces make search and project-review tasks harder to complete.

2.3 Proposed Solution

ResearchX provides an integrated browser interface backed by a PostgreSQL schema. Users can register projects and assign multiple research domains; browse and save papers discovered through OpenAlex; store author associations; create review decisions; and search for related locally indexed records using MiniLM embeddings stored in pgvector.

PostgreSQL constraints enforce entity integrity, referential integrity and valid statuses. Stored procedures support coordinated faculty review operations, triggers maintain timestamps and audit logs, and transaction-based application writes help prevent relational records and vectors from becoming inconsistent.

4. ER TO RELATIONAL MAPPING

4.1 Steps of Algorithm for the Chosen Problem

Step 1 — Mapping regular (strong) entity types

The strong entity sets ROLE, APP_USER, DOMAIN, PROJECT, RESEARCH_PAPER, AUTHOR and PROJECT_REVIEW become base relations with their own primary keys. AUDIT_LOG and EMBEDDING_REF are additional implementation relations. Every relation stores its simple attributes as defined by the SQL schema.

Step 2 — Mapping weak entity types

No weak entity with an identifying partial key is defined in the implemented ResearchX schema. Consequently, no weak-entity mapping transformation is applied. This is deliberate rather than adding an artificial weak entity.

Step 3 — Mapping binary 1:1 relationships

The implemented conceptual relationships do not require a distinct mandatory binary 1:1 mapping. Uniqueness in individual attributes, such as an OpenAlex identifier, should not be misrepresented as an entity-to-entity 1:1 relationship.

Step 4 — Mapping binary 1:N relationships

ROLE(1)–APP_USER(N) is implemented with APP_USER.role_id. APP_USER(1)–PROJECT(N) uses PROJECT.student_id. PROJECT(1)–PROJECT_REVIEW(N) uses PROJECT_REVIEW.project_id, and APP_USER(1)–PROJECT_REVIEW(N) uses faculty_id. PROJECT.approved_by is an optional foreign key to APP_USER.

Step 5 — Mapping binary M:N relationships

PROJECT and DOMAIN are connected through PROJECT_DOMAIN(project_id, domain_id), with a composite primary key and both fields foreign keys. RESEARCH_PAPER and AUTHOR are connected through PAPER_AUTHOR(paper_id, author_id), using the same composite-key technique plus author_order.

Step 6 — Mapping multivalued attributes

The implemented conceptual model does not use independent multivalued attributes requiring a dedicated mapping table. Repeating research domains and authors are represented as relationships with their own association tables, not comma-separated attribute values.

Step 7 — Mapping n-ary relationships

No ternary or higher-order relationship type is required by this design. The two-entity mappings and review entity cover the implemented requirements.

5. DDL STATEMENTS

5.1 Database Creation and Extension

PostgreSQL 16 and pgvector are used for the same relational database. The pgvector extension introduces the VECTOR type, allowing dense vectors to be stored alongside conventional entities. The original setup SQL contains DROP TABLE statements for clean-room initialization; those destructive initialization statements are intentionally excluded from the report's reproduction examples to prevent accidental deletion of a populated database.

CREATE EXTENSION IF NOT EXISTS vector;

5.3 Indexes and Query Performance

-- Indexes for Relational Performance & Vector Retrieval
-- ----------------------------------------------------------------------------
CREATE INDEX idx_project_student ON project(student_id);
CREATE INDEX idx_project_status ON project(status);
CREATE INDEX idx_paper_year ON research_paper(year);
CREATE INDEX idx_paper_openalex ON research_paper(openalex_id);
CREATE INDEX idx_embedding_entity ON embedding_ref(entity_type, entity_id);
CREATE INDEX idx_audit_table ON audit_log(table_name, record_id);

-- HNSW Vector Index for efficient approximate nearest-neighbor cosine queries
CREATE INDEX idx_embedding_vector_hnsw ON embedding_ref 
USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 64);

The relational indexes accelerate commonly filtered columns including project status and student ID, while idx_embedding_vector_hnsw applies Hierarchical Navigable Small World indexing with vector_cosine_ops to the 384-dimensional embedding column.

The index supports efficient approximate nearest-neighbor retrieval. An approximate index trades some recall for improved search performance and does not alter the stored similarity definition.

7. QUERIES

7.1 Simple Query with GROUP BY, Aggregate Functions and HAVING

This query computes the count of projects per domain, their approval statuses and average problem-statement length. LEFT JOIN preserves research domains that have no projects.

SELECT 
    d.domain_id,
    d.domain_name,
    COUNT(pd.project_id) AS total_projects,
    COUNT(CASE WHEN p.status = 'Approved' THEN 1 END) AS approved_projects,
    COUNT(CASE WHEN p.status = 'Pending' THEN 1 END) AS pending_projects,
    ROUND(AVG(LENGTH(p.problem_statement)), 2) AS avg_problem_statement_chars
FROM domain d
LEFT JOIN project_domain pd ON d.domain_id = pd.domain_id
LEFT JOIN project p ON pd.project_id = p.project_id
GROUP BY d.domain_id, d.domain_name
HAVING COUNT(pd.project_id) >= 0
ORDER BY total_projects DESC, d.domain_name ASC;

Recorded output: six research domains were returned. The Artificial Intelligence & Machine Learning domain had six project-domain assignments at the time of evidence capture.

7.4 Correlated Query

For each paper, the correlated subquery determines the average citation count for that paper's publication year. The outer query selects papers exceeding their own yearly cohort average.

SELECT 
    rp.paper_id,
    rp.title,
    rp.year,
    rp.cited_by_count,
    ROUND((
        SELECT AVG(sub.cited_by_count)
        FROM research_paper sub
        WHERE sub.year = rp.year
    ), 2) AS cohort_avg_citations
FROM research_paper rp
WHERE rp.cited_by_count > (
    SELECT AVG(sub.cited_by_count)
    FROM research_paper sub
    WHERE sub.year = rp.year
)
ORDER BY rp.year DESC, rp.cited_by_count DESC;

In the saved output, the HNSW graph paper was above its 2020 cohort mean, with 3,100 citations versus a recorded cohort average of 2,480.

7.5 Nested Query

Two nested IN subqueries find students who own approved projects in the AI/ML research categories. The database performs filtering across APP_USER, PROJECT, PROJECT_DOMAIN and DOMAIN without duplicating user records.

SELECT 
    u.user_id,
    u.username,
    u.full_name,
    u.email
FROM app_user u
WHERE u.user_id IN (
    SELECT p.student_id
    FROM project p
    WHERE p.status = 'Approved'
      AND p.project_id IN (
          SELECT pd.project_id
          FROM project_domain pd
          JOIN domain d ON pd.domain_id = d.domain_id
          WHERE d.domain_name ILIKE '%Artificial Intelligence%'
             OR d.domain_name ILIKE '%Machine Learning%'
      )
);

The recorded sample output contained two demonstration student profiles.

7.6 Additional Multi-Table JOIN

A multi-table query joins the projects to student users, research-domain mappings, optional faculty reviewers, review decisions and embedding availability. STRING_AGG combines a project's multiple domain names into a readable result.

SELECT 
    p.project_id,
    p.title,
    p.status,
    u_student.full_name AS student_name,
    u_student.email AS student_email,
    STRING_AGG(DISTINCT d.domain_name, ', ') AS domains,
    u_faculty.full_name AS reviewed_by_faculty,
    pr.decision AS review_decision,
    pr.comments AS review_comments,
    CASE WHEN er.embedding_id IS NOT NULL THEN 'Indexed (384-d)' ELSE 'Pending Vector' END AS vector_status,
    p.created_at
FROM project p
JOIN app_user u_student ON p.student_id = u_student.user_id
LEFT JOIN project_domain pd ON p.project_id = pd.project_id
LEFT JOIN domain d ON pd.domain_id = d.domain_id
LEFT JOIN app_user u_faculty ON p.approved_by = u_faculty.user_id
LEFT JOIN project_review pr ON p.project_id = pr.project_id
LEFT JOIN embedding_ref er ON p.project_id = er.entity_id AND er.entity_type = 'PROJECT'
GROUP BY 
    p.project_id, 
    p.title, 
    p.status, 
    u_student.full_name, 
    u_student.email, 
    u_faculty.full_name, 
    pr.decision, 
    pr.comments, 
    er.embedding_id, 
    p.created_at
ORDER BY p.project_id ASC;

7.7 pgvector Similarity Query (Additional DBMS Feature)

ResearchX computes cosine similarity as 1 − cosine distance; PostgreSQL's <=> operator returns cosine distance. Query parameters carry the 384-dimensional input embedding. Stored vectors may represent projects or locally saved papers.

SELECT 
    p.project_id,
    p.title,
    p.problem_statement,
    p.status,
    u.full_name AS student_name,
    STRING_AGG(DISTINCT d.domain_name, ', ') AS domains,
    ROUND((1 - (er.embedding <=> $1::vector))::numeric, 4) AS similarity_score
FROM embedding_ref er
JOIN project p ON er.entity_type = 'PROJECT' AND er.entity_id = p.project_id
JOIN app_user u ON p.student_id = u.user_id
LEFT JOIN project_domain pd ON p.project_id = pd.project_id
LEFT JOIN domain d ON pd.domain_id = d.domain_id
GROUP BY p.project_id, p.title, p.problem_statement, p.status, u.full_name, er.embedding
ORDER BY er.embedding <=> $1::vector ASC
LIMIT 5;

An independent repository evidence capture ranked GraphDB-Scale at 0.3515 and BioMedQA at 0.3504 similarity relative to ResearchX's own project vector. These are values observed in one database snapshot, not fixed scores for all queries or models.

8. STORED PROCEDURES, FUNCTIONS AND TRIGGERS

8.1 Stored Procedure: Faculty Project Review

The stored procedure sp_review_and_approve_project checks that the project exists and that the nominated reviewer has a Faculty or Admin role, then inserts a review and updates the project status in a single database transaction context. Its actions also activate the audit trigger.

The following script is the final version of the stored-procedure, function and trigger definitions in database/procedures_triggers.sql.

CREATE OR REPLACE PROCEDURE sp_review_and_approve_project(
    p_project_id INTEGER,
    p_faculty_id INTEGER,
    p_decision VARCHAR(30),
    p_comments TEXT
)
LANGUAGE plpgsql
AS $$
DECLARE
    v_role_name VARCHAR(30);
    v_project_exists BOOLEAN;
    v_new_status VARCHAR(30);
BEGIN
    -- Verify project exists
    SELECT EXISTS(SELECT 1 FROM project WHERE project_id = p_project_id) INTO v_project_exists;
    IF NOT v_project_exists THEN
        RAISE EXCEPTION 'Project with ID % does not exist', p_project_id;
    END IF;

    -- Verify that the reviewer is Faculty or Admin
    SELECT r.role_name INTO v_role_name
    FROM app_user u
    JOIN role r ON u.role_id = r.role_id
    WHERE u.user_id = p_faculty_id;

    IF v_role_name IS NULL OR v_role_name NOT IN ('Faculty', 'Admin') THEN
        RAISE EXCEPTION 'User % is not authorized as Faculty or Admin to review projects', p_faculty_id;
    END IF;

    -- Map review decision to project status
    IF p_decision = 'Approved' THEN
        v_new_status := 'Approved';
    ELSIF p_decision = 'Rejected' THEN
        v_new_status := 'Rejected';
    ELSE
        v_new_status := 'Pending';
    END IF;

    -- Perform atomic updates
    -- 1. Insert faculty review record
    INSERT INTO project_review (project_id, faculty_id, decision, comments, review_date)
    VALUES (p_project_id, p_faculty_id, p_decision, p_comments, NOW());

    -- 2. Update project status and approval faculty ID
    UPDATE project
    SET status = v_new_status,
        approved_by = CASE WHEN p_decision = 'Approved' THEN p_faculty_id ELSE NULL END,
        updated_at = NOW()
    WHERE project_id = p_project_id;

    -- Note: Trigger trg_audit_project_changes will automatically record the audit entry!
END;
$$;

8.3 Trigger for Project Timestamps

trg_project_timestamp fires BEFORE UPDATE and sets NEW.updated_at = NOW() to ensure that a modified project carries a new timestamp.

CREATE OR REPLACE FUNCTION fn_trg_project_timestamp()
RETURNS TRIGGER AS $$
BEGIN
    NEW.updated_at = NOW();
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

DROP TRIGGER IF EXISTS trg_project_timestamp ON project;
CREATE TRIGGER trg_project_timestamp
BEFORE UPDATE ON project
FOR EACH ROW
EXECUTE FUNCTION fn_trg_project_timestamp();

8.4 Trigger for Project Audit History

trg_audit_project_changes records meaningful project INSERT, DELETE and selected UPDATE operations in AUDIT_LOG. Old and new values are stored as JSONB so the historical change is inspectable.

CREATE OR REPLACE FUNCTION fn_trg_audit_project_changes()
RETURNS TRIGGER AS $$
BEGIN
    IF (TG_OP = 'UPDATE') THEN
        IF (OLD.status IS DISTINCT FROM NEW.status OR OLD.title IS DISTINCT FROM NEW.title) THEN
            INSERT INTO audit_log (table_name, action, record_id, old_values, new_values, changed_at)
            VALUES (
                'project',
                'UPDATE',
                NEW.project_id,
                jsonb_build_object(
                    'title', OLD.title,
                    'status', OLD.status,
                    'approved_by', OLD.approved_by,
                    'updated_at', OLD.updated_at
                ),
                jsonb_build_object(
                    'title', NEW.title,
                    'status', NEW.status,
                    'approved_by', NEW.approved_by,
                    'updated_at', NEW.updated_at
                ),
                NOW()
            );
        END IF;
        RETURN NEW;
    ELSIF (TG_OP = 'DELETE') THEN
        INSERT INTO audit_log (table_name, action, record_id, old_values, new_values, changed_at)
        VALUES (
            'project',
            'DELETE',
            OLD.project_id,
            jsonb_build_object(
                'title', OLD.title,
                'status', OLD.status,
                'student_id', OLD.student_id
            ),
            NULL,
            NOW()
        );
        RETURN OLD;
    ELSIF (TG_OP = 'INSERT') THEN
        INSERT INTO audit_log (table_name, action, record_id, old_values, new_values, changed_at)
        VALUES (
            'project',
            'INSERT',
            NEW.project_id,
            NULL,
            jsonb_build_object(
                'title', NEW.title,
                'status', NEW.status,
                'student_id', NEW.student_id
            ),
            NOW()
        );
        RETURN NEW;
    END IF;
    RETURN NULL;
END;
$$ LANGUAGE plpgsql;

DROP TRIGGER IF EXISTS trg_audit_project_changes ON project;
CREATE TRIGGER trg_audit_project_changes
AFTER INSERT OR UPDATE OR DELETE ON project
FOR EACH ROW
EXECUTE FUNCTION fn_trg_audit_project_changes();

8.5 Trigger for Embedding Cleanup

Because EMBEDDING_REF uses a polymorphic reference, it cannot enforce a single conventional foreign key to both PROJECT and RESEARCH_PAPER. The cleanup trigger deletes the corresponding vector record before either parent is deleted.

CREATE OR REPLACE FUNCTION fn_trg_cascade_delete_embeddings()
RETURNS TRIGGER AS $$
BEGIN
    IF (TG_TABLE_NAME = 'project') THEN
        DELETE FROM embedding_ref 
        WHERE entity_type = 'PROJECT' AND entity_id = OLD.project_id;
        RETURN OLD;
    ELSIF (TG_TABLE_NAME = 'research_paper') THEN
        DELETE FROM embedding_ref 
        WHERE entity_type = 'RESEARCH_PAPER' AND entity_id = OLD.paper_id;
        RETURN OLD;
    END IF;
    RETURN OLD;
END;
$$ LANGUAGE plpgsql;

DROP TRIGGER IF EXISTS trg_cascade_project_embeddings ON project;
CREATE TRIGGER trg_cascade_project_embeddings
BEFORE DELETE ON project
FOR EACH ROW
EXECUTE FUNCTION fn_trg_cascade_delete_embeddings();

DROP TRIGGER IF EXISTS trg_cascade_paper_embeddings ON research_paper;
CREATE TRIGGER trg_cascade_paper_embeddings
BEFORE DELETE ON research_paper
FOR EACH ROW
EXECUTE FUNCTION fn_trg_cascade_delete_embeddings();

8.6 Transactions and Integrity Testing

ResearchX tests transaction rollback during multi-step changes so a failed operation does not leave a partial relational/project embedding combination. This is relevant to the DBMS ACID atomicity property: all statements in a transaction succeed or the transaction's changes are rolled back.

The repository's automated evidence reports 13 of 13 platform integration checks passing, including project creation, faculty review, OpenAlex search/save, real similarity search, and cleanup of created project and paper records. A separate transaction-rollback test supplies further evidence.
